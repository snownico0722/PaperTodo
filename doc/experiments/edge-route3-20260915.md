## 1. 实验在比较什么

候选基于 `26142c1d1d055c35e2b1c8843cee6030203a31cc`，即 **#260 候选与当时主线的整合基线**，已包含静态预接管、代理复用及 render demand；没有带入 E-016 未采用的 HWND 候选。

路线 3 尝试由原生代理执行宽高、裁剪、圆角和整体透明度动画，正文仍由实际 WPF 绘制。每个获准 Host 增加一个有界、隐藏且不接收输入的 atlas HWND，用 VisualBrush 提供分层内容，真实输入窗口保持正常布局与透明度。文字不缩放，不复制正文控件或业务 model。

这并未消除 WPF 首次布局、动态内容绘制和最终交接。新增成本包括隐藏 HWND、atlas surface、VisualBrush 引用、布局就绪判断，以及换代时等待旧消费者和合成提交完成的资源退休过程。

实验包默认开启 native shape；Debug 包可用 `PAPERTODO_EDGE_PROXY_SHAPE_EXPERIMENT=0` 关闭，进行同包 OFF/ON 对照。脚本中旧的 `RenderDemand=false` 元数据不控制产品，原记录通过 `scheduler.demand.mode=1` 核对了实际启用状态。

**OFF 是同一历史候选包关闭路线 3，不是当前 main。** 文档拆分基线 `4adebd559da172bca4db5cfa3dc7ac3c6464c040` 中，D-037 仍为 Deferred，D-038 为 Accepted。此次复盘既不把 #260 候选升级为已采用方案，也不撤销主线已有实现。

### 2.1 共享真实 Root alpha 的前置失败

先前共享真实 Root alpha 的候选，在受控 ROI 捕获中出现普通交接短暂变亮；插入 80 ms 通道延迟时又出现短暂变暗。但初版夹具没有使用产品完整的 batch 回调，**不能把观察到的时长当作真实产品交接时长**。

使用真实 batch 回调的纠正夹具在原记录中仍为未运行。后续独立 atlas 不再沿用共享 alpha 的交接办法，但更换办法本身并不证明像素和交接已经正确。

### 2.2 准备回归的原因与修复

队列 placement 会刷新每个 Host 的主题，新增源逻辑却无条件失效，即使颜色不变也让每轮 10 个 atlas 全部重建。

实验随后按实际采样外壳样式判断是否换代；等值主题保留源。预览布局尚未就绪、临时回退到真实 HWND 时，在最后租约释放后保留唯一有效的当前 atlas；再次获取仍核对布局、owner、容量、DPI 和原生身份。隐藏、关闭、失效和退休代继续回收，没有移除原有合成退休屏障。

另外，同尺寸正文替换可能因描述值相等而漏增 Revision、漏发 Updated，因此资源兼容性不能只看宽高；内容身份也需要参与失效判断。这些是失败候选中的修复经验，不表示相关缓存和生命周期实现需要留在产品中。

## 3. 性能结果

### 3.1 跨版本只能比较共同的前 30 个动作

| 包与开关 | 代理准备 P50（ms） | 代理准备 P95（ms） |
| --- | ---: | ---: |
| v3 OFF | 1.9607 | 17.5389 |
| v3 ON | 265.8014 | 348.4680 |
| v5 ON | 45.3492 | 89.2661 |
| v7 ON | 27.4086 | 99.6240 |
| v7 OFF | 1.8993 | 18.8556 |

原记录以共同 30 动作核对 v3 OFF/ON，并以完全相同的前 30 动作比较 v3 ON、v5 ON、v7 ON、v7 OFF。不能把前缀统计与完整 36 动作混用。v5 到 v7 的中位数下降，但 P95 没有同步下降，不能概括成“所有尾部都改善”。

### 3.2 最终 v7 同包 OFF/ON：完整同序 36 动作

| 指标 | OFF | ON |
| --- | ---: | ---: |
| 代理准备 P50（ms） | 1.8993 | 31.9784 |
| 代理准备 P95（ms） | 18.8556 | 99.6240 |
| 首次启动准备（ms，单样本） | 52.5088 | 424.6578 |
| 整轮进程 CPU 时间（s） | 6.703125 | 9.015625 |
| 终点 Private Bytes（MiB） | 269.828125 | 314.25 |

**每组仅一轮。** 这些值支持“这轮接入尚未证明优于关闭状态”，不支持可推广的固定倍率、显著性或长期内存结论。终点 Private Bytes 不是峰值内存，也不是长期泄漏测试；整轮 CPU 时间不是 CPU 占用率。

当时仍存在首次准备成本、部分预览 `source-unavailable` 回退，以及提交退休等待。WPF 软件更新间隔不等于原生动画实际出屏帧率，不能用它直接推导物理 FPS 或输入到显示的延迟。

## 4. 独立动画能力成立，但产品接入没有通过

`--proxy-animation-value` 复用实际 Host 和 DXGI ROI 夹具，只比较已准备好的真实 HWND 与 native shape，执行展开和反向；它不是完整鼠标回放。

两组的两段 UI 阻塞期间，Host.Apply 和原生 shape 再提交增量均为 0。原记录在严格 QPC 窗口内排除段首 75 ms：

| 已准备好的路径 | 展开 | 反向 / 收回 |
| --- | --- | --- |
| 真实 HWND | 8 个有效样本保持同一幅图像 | 28 个有效样本保持同一幅图像 |
| native shape | 11 个有效样本，11 幅不同 RGB 图像 | 29 个有效样本，23 幅不同 RGB 图像 |

这说明原生代理在 UI 不继续提交形状时仍有动画能力，但当时静态起点仍有 **119 个像素超过 RGB 容差 2**，UI 阻塞的收回末端勾形图标也未及时恢复。实验只覆盖单边缘、单样例、每组一次；预先准备排除了最昂贵的一段，不能据此宣称整体更快。

实际输入、多屏 / 混合 DPI 和完整像素验收尚未完成。它们应记为“未完成，因而未满足采用条件”，而不是“已观察到所有这些场景失败”；已经观察到的像素偏差和图标恢复问题则应明确保留。

## 5. 停止采用的理由与可复用经验

**停止的是这版产品接入，不是否认独立动画能力。** 修掉候选自身造成的大量重建后，准备成本、CPU 和终点私有内存仍未展示优于关闭状态的结果；同时增加了资源生命周期、布局就绪、交接和像素一致性的维护负担。已有证据不足以支持继续把它当成可合并功能推进。

### 先验证收益，再扩大接入

先用最小、真实的样例区分“机制能不能工作”和“用户操作是否更快”，再决定是否扩展资源管理。只展示预先准备好的外壳会动，不能抵消第一次准备、内容完成和输入交接的成本。

### 修复自身回归不等于优化现有产品

从 v3 ON 大幅降到 v7 ON，说明候选中的严重重复工作被修掉了。采用判断仍要回到同包 OFF/ON，不能只和最差的实验版本比较，也不能把含 #260 候选的 OFF 写成当前 main。

### 失效判断需要同时识别“没变”和“真的变了”

等值主题不应重建全部资源；同尺寸正文替换也不能漏掉内容更新。缓存必须明确内容身份、布局、DPI、容量与生命周期边界，不能用减少失效次数掩盖陈旧内容。

### 外壳动画、端点内容与真实输入分开验收

形状能持续变化，不代表终点图标、透明度、真实点击或控制权交接正确。真实端点验证和旧资源安全退休是独立要求；不能为降低准备数字而跳过这些边界。

### 保持测量口径和夹具边界一致

比较相同 action/owner，跨版本只取共同前缀，标明单轮和单样本。确认运行时实际开关，不以脚本的过期标签代替运行证据。夹具应复用真实产品回调；注入延迟和软件采样只能支持各自覆盖的结论。

### 保留知识，不给失败路线增加长期维护义务

保留负面结果、少量关键数据、证据边界和失败原因即可。失败候选的产品代码、专用检查、诊断入口、默认开关和资源管理框架不因这份复盘进入主线。当前不采用不构成永久禁令，但以后重开需要新的可验证收益，不能只重复已准备样例的能力演示。
