# 侧边文字预览：少对象，而非继续换引擎

本记录是 #245 的实验续篇，不替代 [正式架构](../../doc/ARCHITECTURE.md)，不批准 main 合并。性能比较基线是组合版 `14c7223190b1198941d7ce450e3cf52ee83ed73e`，不是 main 或旧 #238。没有更改 #243、#238 分支。

## 本轮接纳与拒绝

仅接纳短文本字体样式对象精简：加粗、斜体和代码字体直接设置到已有 Run，保留真实 Hyperlink、相邻同 URL 链接的独立身份、动态资源与原来的字体优先级。删除线和下划线仍用原 Span 作用范围。

两处测试改为按相同文字找到 Run，再检查原有字体、字号、字重和缩放要求；没有放宽这些要求。生产改动只有 `EdgeCapsulePreview.Markdown.Inlines.cs`。不改字符预算、布局尺寸策略、动画、计时器、输入路由、取消、一次发布或存储。

第一次同时试过全部样式压平与取消复制样式数据时的分批步骤。[两变量运行 34631857210](https://github.com/snownico0722/PaperTodo/actions/runs/34631857210) 有多链接就绪延迟反例：增强 20.78→23.52ms，完全渲染合并中位数 15.04→15.57ms，后者第二轮单独为 14.79→32.52ms。因为同时改了两个因素，不能把差异归因于其中一个。最终不纳入复制阶段的调度改动，长段落分批代码与基线一致。

全部压平还带来局部删除线/下划线像素变化。即使低于既有 2% 检查阈值，也没有直接视作相同；收窄为只精简字体样式，恢复装饰线作用范围后重新完整验证。

同一 Windows runner、同一真实 EdgeCapsuleHost/Presenter、固定 460×410 卡片、160ms 动画。按旧→新→新→旧运行四个独立进程，每种场景每进程 3 次预热、21 次正式新视图样本；每个版本每场景合计 42 个预热后样本。新旧探针相同，原始预热和正式记录均保留。每次新建视图不等于每次应用冷启动。

五种输入字符数为 251、290、3150、5508、3960；6000 是上限，不是每个样本的长度。扩大样本与交换顺序不能消除所有 runner/字体缓存/调度波动，也不足以宣称线上 p95。就绪是 WPF 布局就绪，不是 GPU 呈现；最大回调间隔不是屏幕帧率；分配量不是常驻内存。

## 正确性

七组 Release：实验、MarkdownSemantic、MarkdownEditing、TodoNavigation、EdgeTitle、Threading、Persistence 全部退出 0；Debug 实验通过。

128 组像素对照覆盖四档模式、两种字体/清晰度配置、两档缩放、八种输入。127 组全部字节一致；剩余一组为 537600 字节中 122 字节不同，最大通道差值 6/255，没有超过 32 的差异。未把它写成 128 组字节完全一致，也未断言剩余微差必定来自某种已定位原因。真实混合 DPI、辅助功能、跨胶囊交接和鼠标手势仍不等于被这项像素检查全面覆盖。

## 官方项目经验与下一步

- [WPF 文字性能](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-text)：高级文字对象有代价；应控制对象数量，不能将示例数字当成 PaperTodo 性能。
- [WPF 高级文字格式化](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/advanced-text-formatting)：TextFormatter 负责系统排版，官方也示范把 TextLine 绘制结果存入 DrawingGroup。提供样式数据并保留结果，不等于自行发明断行或字体引擎。
- [WPF 布局](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/optimizing-performance-layout-and-design)、[CodeMirror 更新周期](https://codemirror.net/docs/guide/#update-cycle)：优先减少重复布局，保持内容和最终宽度稳定；不同宽度不能强行套用旧折行。
- [VS Code 2017 年工程记录](https://code.visualstudio.com/blogs/2017/02/08/syntax-highlighting-optimizations)：紧凑样式数据和减少转换值得借鉴，不是必须迁移到 Web。
- [Avalonia #21030](https://github.com/AvaloniaUI/Avalonia/pull/21030) 缓存重复字形工作；[#21902](https://github.com/AvaloniaUI/Avalonia/issues/21902) 又报告失效窗口导致空缓存持续生效。它是另一框架的上游案例，不能直接归因给本项目；复用必须有内容身份和失效规则。
- [Scintilla 布局缓存与并行条件](https://www.scintilla.org/ScintillaDoc.html#LineWrapping)：缓存可限到可见页面；并行测量要求底层线程安全，不能直接把 WPF 控件交给后台线程。

优先补“单行 100—255 字符但样式密集”的样本，再决定是否由样式片段数辅助当前长度分流。其次分别测试首次悬停、A→关闭→A、A→B→A，以及内容/主题/缩放/DPI 变化，再决定是否加入严格限量的最近预览结果缓存。当前尚未实现这些候选，不凭文档经验宣称它们已经提速。

共享整段版本化语义可收敛跨行与引用定义的一致性，但不是当前长行排版大头的直接解药；也不能为复用而暗中解析整篇十万字符。继续保持一个生产组合路径，正式选型收尾时再清理完整 AvalonEdit 对照原型。不要因此原样合并 #243，#238 动画仍单独审查。
