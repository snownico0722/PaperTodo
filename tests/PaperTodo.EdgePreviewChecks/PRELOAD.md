# 高负载侧边预览全量预热实验

本分支基于 #245 `ae1eb739464dc04e7cc23b8d749cb4ed7aa24f60`。预热仍是现有 Markdown 预览的可丢弃优化，不是另一套渲染器，也不改变 #238 动画层。

## 当前实验策略

不再依据鼠标附近的胶囊、队列邻居或最近使用数量选择目标。每张可见的内置 Markdown Note 只看自己的 **16 块 / 6000 字符有界摘要**：

- 16 块 / 6000 字符有界摘要的总字符数 **> 400**；或
- 总字符数 **> 200**，并且其中带 Markdown 样式/链接语义的可见字符数 **> 100**；或
- 总字符数 **> 200**，并且 Markdown 样式/链接片段数 **> 3**。

两个比较都是严格大于。围栏代码正文按 Markdown 样式字符计入；Markdown Off 时只有总字符数 >400 这一条生效。规则用于判断“是否值得空闲预排版”，不再复用 #245 的单段渲染分流阈值。

明显高负载的 Note 在内容/胶囊初始化后，先经过 **500ms 单次 debounce** 合并启动/编辑阶段的连续变化，再于 `ContextIdle` 空闲优先级排队完成完整预排版；**不按数量淘汰**，每张重 Note 最多保留一份当前版本的完成正文。普通短文本不做产品预解析、不做完整预排版，也不会挤掉重 Note。正式悬停会立即取消当前投机工作，正常打开优先；剩余重 Note 队列之后继续。

已有 pointer-over / preview-complete 调用只作为“当前这张此前因宿主尚未就绪而失败时再试一次”的兜底，不扫描邻居，不决定其他 Note 是否预热。主要调度来自每张 Note 自己的内容/胶囊初始化与失效。

缓存键继续包含内容版本、实际摘要、模式、缩放、精确视口尺寸、DPI、字体/语言和动态资源颜色。内容、主题、尺寸、模式或 DPI 改变后不能沿用旧排版；取消和过期工作不能发布。一个完成正文同时只能属于缓存或一个实际预览树。

## 为什么改掉“最近四张”

初版 #246 证明：只提前解析 Markdown 并不是稳定收益；真正显著的是 **完整排版命中**。同机初版实验中，密集长行 Enhanced 由 72.43ms 降到 1.63ms，Full 由 56.97ms 降到 1.05ms；短密集多行也约为 1ms。普通短行完整预热收益很小，而且仍要承担控件重新挂载，所以不值得主动做。

因此当前实验把选择问题从“用户接下来可能指向哪张”改成“哪张内容本身明确昂贵”。

## 高负载方案同机结果

运行 [34644485740](https://github.com/snownico0722/PaperTodo/actions/runs/34644485740)。同一 Windows runner、真实 Host/Presenter、460×410 卡片、160ms 动画；正序/逆序两个进程，每种策略每场景排除前两次预热，合并 14 个正式样本。

正文布局就绪中位数（ms；不是动画时长或 GPU 呈现）：

| 场景 | 模式 | 不预热 | 仅预解析诊断 | 完整排版命中 |
|---|---|---:|---:|---:|
| 普通短行 | Enhanced | 45.85 | 38.92 | **不预热 / 0 次 body hit** |
| 普通短行 | Full | 24.72 | 16.92 | **不预热 / 0 次 body hit** |
| 密集长行 | Enhanced | 110.96 | 99.32 | **2.60** |
| 密集长行 | Full | 101.42 | 89.41 | **1.28** |
| 短密集多行 | Enhanced | 56.30 | 44.58 | **1.45** |
| 短密集多行 | Full | 45.86 | 27.69 | **1.18** |

普通短行 `layout` 探针现在会被分类器直接拒绝，body hit 始终为 0；不同运行顺序下其冷路径波动很大，因此不把探针顺序造成的毫秒差写成预热收益。`text` 列只保留用于证明“纯预解析并非产品级解法”，产品调度不调用它。

重内容完整预热本身仍要在打开前付出工作：密集长行约 73–101ms、短密集多行约 27–55ms 的合并中位数（包含 ContextIdle 协作等待），成本只是搬到空闲期，并未消失。命中后需求侧 UI 分配也明显降低，但这里不把分配量等同于常驻内存。

## “不限制数量”的真实内存代价

同一运行专门创建 **100 张、每张 6000 字符且密集样式的明显重 Note**，完整 GC 后测量托管存活堆：

- 100 份有界摘要 / 语义准备结果：`6390 KiB`，约 **6.24 MiB**；
- 100 份完成排版 + 本阶段 WPF 内部缓存：`105965 KiB`，约 **103.48 MiB**；
- 合计约 **109.72 MiB managed live heap**。

换算下来，这组最坏样本的完成排版大约 **1.03 MiB / 重 Note**。100 份预热与内存测量这一步在 CI 中约 10 秒完成，但这包含测试、GC 和 WPF 环境，不能当作实际启动时间。

这个结果很重要：**“不按数量淘汰”技术上可行，但并不是几乎零内存。** 十来张明显重 Note 仍是十几 MiB 量级；如果用户真的长期保留上百张最坏输入，额外一百多 MiB 对 PaperTodo 这种轻量桌面程序已经不可忽略。这里统计的是托管存活堆增量，不含源样本、进程原生内存、字体系统、DComp/GPU 和完整工作集。

因此 #246 继续保持 Draft，用来验证用户提出的“重的全量预热、轻的不预热”是否值得采用。当前代码按字面实验 **不设数量上限**，但正式合入前应结合真实重 Note 数量决定是否保持完全无上限，或者只加内存压力保护；不再回到鼠标邻居预测或固定 4 张 LRU 作为主要策略。

## 正确性

当前重载实验的 EdgePreview Release 行为检查、正反性能探针、100 重 Note 内存检查全部通过。此前 #246 已验证 A→B→A 跨视图命中、内容/版本/颜色/视口/缩放/模式/DPI 失效、取消/迟到任务和 24 组冷/热像素逐字节一致；这些边界没有因选择策略变化而放宽。

真实混合 DPI、快速连续跨胶囊、长期真实命中率、预热期间与 240Hz 动画同时运行的体验仍需真机验证。
